PRODUCT & FUNCTIONAL REQUIREMENTS
Blu Visual Teacher Hackathon | Offline-first implementation blueprint
Prepared from the supplied six-page hackathon problem statement, with implementation recommendations and repository research clearly separated from mandatory requirements.
1. Executive summary
Blu Visual Teacher is a local-first teaching-video engine. A learner enters a concept, level, language and target duration. A local language model produces a schema-validated lesson plan. The application renders deterministic animated scenes, generates narration and captions using local models, synchronizes scene timing to the actual audio, and exports a 1280×720 MP4 plus structured JSON study notes. It must operate with Wi-Fi disabled after setup.

3. Product goals and success criteria
A user can enter a new topic and receive a playable lesson and two downloadable artifacts: lesson.mp4 and lesson-notes.json.
The same lesson can be generated in English and at least two chosen Indian languages without requiring a new topic plan for every language.
Scene timing follows generated narration duration, not hard-coded guesses.
The app remains demoable if Ollama or another model call fails, using a bundled sample lesson and pre-generated fallback assets.
All runtime dependencies, model files, fonts and assets are local; a clean offline demo succeeds with Wi-Fi disabled.
The README lists model, voice, code and asset licences plus tested laptop specifications.
4. Target users and primary journey
Primary user: a student or teacher who wants a concise, visual explanation of a concept in a familiar language.

8. Proposed data contracts
8.1 LessonPlan (internal JSON)
Required top-level fields: schema_version, title, level, source_language, target_language, target_duration_seconds, scenes[]. Each scene has id, type, heading, narration, and typed content. Optional fields: visual description, source references, glossary, learning objectives.
Allowed scene types for MVP: title_card, diagram, code_walkthrough. Unknown types are rejected or mapped to fallback; arbitrary HTML/JS/Python from the model is forbidden.
8.2 JSON notes export
Suggested fields: title, language, level, summary, learning_objectives[], key_concepts[{term, definition}], steps[], examples[], key_takeaways[], revision_questions[{question, answer}]. Use UTF-8 and ensure non-Latin script survives round-trip.
8.3 Artifact manifest
Suggested manifest: lesson_id, plan_version, language, duration_seconds, video_path, notes_path, subtitle_path (optional), model_versions, created_at, fallback_used, timings_by_stage.

10. Error handling and fallback policy
Planner timeout/model unavailable → use prevalidated sample plan.
Invalid JSON/schema mismatch → one constrained retry; if still invalid, use sample plan.
Translation unavailable → show explicit language failure; do not silently label English audio as translated. For the main demo, bundle fallback audio for every required language.
TTS failure → use pre-generated fallback audio for the sample lesson; never export a silent or misleadingly labelled video.
FFmpeg/render failure → preserve plan and notes, show export error, and keep fallback MP4 downloadable.
Missing font glyphs → fail language preflight and use bundled Noto fonts; verify captions in actual MP4.
11. Repository reuse plan
Repository research sources: Inkling documents SVG/CSS → deterministic frames → FFmpeg MP4 and an MIT licence (https://github.com/ahkamboh/inkling); Ollama documents schema-constrained JSON output (https://github.com/ollama/ollama/blob/main/docs/api.md); IndicTrans2 documents 22 scheduled languages and MIT model checkpoints (https://github.com/AI4Bharat/IndicTrans2); pguso/kokoro documents offline CPU inference and supported voice list (https://github.com/pguso/kokoro). All components and their actual model weights must be independently audited before use.
12. Recommended MVP architecture
Recommended default: React/Vite/TypeScript UI + FastAPI orchestration + Ollama planner + local TTS/translation adapters + one deterministic renderer + FFmpeg + local filesystem/SQLite. Pick either Inkling-style HTML/SVG frame capture or Remotion. For a 24-hour build, Inkling is a particularly direct reference for deterministic SVG/CSS scenes and FFmpeg assembly, while the team can keep its own JSON schema and UI.
13. Definition of done
Generate a new lesson from a typed topic and selected language/level/duration.
At least three scene types render correctly and are navigable in browser.
English plus two selected Indian languages have local narration and correct-script captions.
A new lesson exports to 1280×720 H.264/AAC MP4 and valid JSON notes.
Scene timing derives from real narration audio durations.
Wi-Fi-off demo passes on the target laptop; CPU-only path works.
Fallback path works when the planner is unavailable or returns invalid data.
README includes setup, model/voice/assets licences, tested specs, offline instructions and known limitations.

16. Suggested 24-hour build order
Hours 0–2: agree schema/API, pick renderer, download dependencies/models, create repo and sample JSON.
Hours 2–5: hard-coded lesson renders in browser and exports MP4 + notes JSON. This is the first gate.

17. Open decisions to resolve immediately
Which two Indian languages will be supported in the demo? Choose based on available tested local voices.
Will the renderer be Inkling-style Puppeteer + FFmpeg or Remotion? Choose one by hour 1.
Which local TTS model can produce acceptable narration in all three demo languages within the laptop budget?
Which small Ollama model has acceptable JSON reliability and CPU latency on the 8–16 GB target?
Is MP4 caption burn-in the default? Recommended for reliable playback; optional SRT is a bonus.
18. Exact repository shortlist — what to use, not just consider
This is the recommended adoption plan for the hackathon. Keep the application small and local. Do not clone every candidate repository or merge whole applications together. Reuse the narrow components/models identified below.
19. Final stack decision
Frontend: React + Vite + TypeScript (new small app; no need to adopt a whole frontend repository).
Backend/orchestration: Python + FastAPI + Pydantic (new thin API service).
Local planner: Ollama + one small pre-downloaded instruction model.
Renderer: Inkling-style deterministic SVG/CSS scene rendering and local browser capture, plus FFmpeg. If Inkling code does not adapt quickly, implement the minimal renderer directly rather than losing hours; Remotion is the single alternative.
Translation: IndicTrans2 only after a language-pair benchmark confirms runtime and quality.
Narration: benchmark Kokoro ONNX and IndicF5 for the exact three demo languages; pick the smallest reliable local path. A pre-generated local sample voice track is mandatory as fallback.
Outputs: lesson.mp4 and lesson-notes.json. Optionally provide lesson.srt.
Do not include WhisperX/ASR in the core pipeline unless the team chooses to verify speech with ASR; TTS audio durations are the timing source for generated lessons.

21.3 Renderer decision: how the repo is actually reused
Default path: inspect Inkling's render.js/build.sh/scene examples and reuse the deterministic render pattern only if it can be adapted quickly to the team’s schema.
Blu must render only three allowlisted component types: title_card, diagram, code_walkthrough. The LLM provides typed fields, not HTML, JS, CSS or Python source.
If adapting Inkling would require broad changes or its shell scripts create Windows friction, stop porting it and implement a minimal renderer with the same concept: local HTML/SVG scenes → Puppeteer/Playwright screenshots or frame sequence → FFmpeg.
Remotion is the one alternative. Decide by hour 1 after a short spike; do not combine renderers.
Export must include audio and captions. Verify the final MP4 itself, not only the browser preview.
21.4 Language plan and TTS decision gate
Pick two Indian languages only after testing a short 2–3 sentence sample on the exact target hardware. English + Hindi + Kannada is a plausible candidate set, but do not promise it until the chosen local voices pass.
For English/Hindi, benchmark Kokoro's actual local voice files. Its repo lists Hindi voices but not Tamil/Telugu/Kannada voice IDs.
For additional Indian languages, benchmark IndicF5 and/or IndicParler-TTS. Check the required reference audio/transcript inputs and model-weight licences.
Run TTS on CPU on the weakest laptop or the intended demo machine. Record cold-start time, warm inference time, peak RAM and output audio quality.
If live TTS is too slow, keep a pre-generated local fallback for the bundled sample lesson in every required language. Do not falsely label English speech as a translated voice.
Use a bundled Noto font subset for each script and visually inspect both browser captions and burned-in MP4 captions.
21.5 Audio timing and export contract
Synthesize narration separately for each scene, preferably as WAV/PCM intermediate assets.
Record a manifest per scene: scene_id, audio_path, duration_seconds, language, voice_id, sample_rate, and optional caption segments.
The renderer uses measured duration_seconds plus a small pause/transition; it must not assign arbitrary fixed scene durations.
Keep a cumulative timeline and derive each scene's start/end from the sum of prior measured durations; use the same timeline for caption placement and export.
Final MP4 requirements: 1280×720, H.264 video, AAC audio, playable with common browsers/players. Burn captions into the video for robust viewing; optionally also export SRT.
Validate with ffprobe or equivalent: dimensions, codecs, duration, audio stream presence and output file size.
21.6 Notes JSON specification
The notes file is a separate required artifact, not a copy of the internal scene plan. Generate it from the validated canonical lesson data. Recommended required keys:
schema_version, title, topic, language, level, summary, learning_objectives[], key_concepts[{term, definition}], step_by_step_explanation[], examples[{description, code?, output?}], key_takeaways[], revision_questions[{question, answer}], generated_artifacts[{type, filename}], model_metadata{planner, translator, tts}.
Serialize as UTF-8 JSON and preserve Unicode characters directly; do not corrupt Devanagari/Tamil/Telugu/Kannada script through ASCII-only conversion.
Validate JSON before exposing the download; include no comments or trailing commas.
Do not invent unsupported facts in notes. Keep the notes grounded in the approved lesson plan and, if present, supplied source content.
If fallback plan is used, the notes must describe that fallback lesson and metadata should record fallback_used=true.
21.7 API and frontend behavior
UI stages: Validating input → Planning lesson → Translating → Generating narration → Rendering scenes → Exporting MP4 → Ready.
The Generate button is disabled while a job is active; errors show a retry or fallback state rather than a spinner forever.
The frontend can use mocked endpoints and fixtures until the backend is ready; no UI work should block on AI integration.
The browser player should offer play/pause, next scene, replay, caption visibility and progress. On phones, avoid heavy DOM animations and use pre-rendered MP4 for smooth playback.
21.8 Security, offline, licences and distribution
Model output is untrusted data. Validate types, lengths, numeric ranges, allowed IDs, allowed scene types and URL fields. Never execute code emitted by the LLM.
Block remote asset loading in rendering; all fonts, icons, audio, scripts and images must be local.
Use network monitoring or disable Wi-Fi for the acceptance test. Ollama's local endpoint is acceptable; any hosted endpoint is not.
Before the event, download model weights, tokenizers, voices, fonts, Python wheels/npm packages and Puppeteer/Chromium binaries needed by the renderer.
Audit licences independently for source repository, model weights, voice packs, sample/reference audio, fonts, FFmpeg build and any included visual assets.
Document model/version, quantization, licence URL, language, voice ID, file size and tested RAM/runtime in README.
Do not bundle large model files in Git; provide a local setup script that checks whether expected files exist and fails with an offline-friendly message.

21.10 Final acceptance test script

21.11 What is explicitly not in the 24-hour MVP
Uploading and translating existing MP4 videos (Chitralekha-style workflow).
A full chatbot, user accounts, cloud storage, remote analytics or online collaboration.
Dynamic model-generated JavaScript/Python/HTML execution.
Multiple competing rendering frameworks in one build.
ASR-based timing for generated narration when audio duration is already known.
Voice marketplace, advanced caching, many extra scene types, complex motion design or a lesson library.

GET /api/lessons/{id}/status | No body | Return {status, stage, progress_percent, message, fallback_used}.
GET /api/lessons/{id} | No body | Return validated lesson plan, notes metadata, artifact manifest and warnings.
GET /api/lessons/{id}/video | No body | Stream/download video/mp4 only after export passes validation.
GET /api/lessons/{id}/notes | No body | Download lesson-notes.json as application/json.
GET /api/lessons/{id}/subtitles | No body; optional | Download SRT if generated.
Metric | Target / measurement
Offline correctness | 100% of acceptance run succeeds with Wi-Fi off.
Video format | 1280×720, H.264, AAC; duration within target range where possible.
Scene sync | No audible narration is cut off; transitions and captions follow measured audio durations.
Planner | Record cold-start and warm generation time; use a small model and bounded output.
TTS | Measure per-language cold start, synthesis time per scene, real-time factor and peak RAM.
Memory | Record peak resident memory on the target laptop; avoid simultaneous loading of planner, translator and TTS if RAM pressure is high.
Fallback | Known-good sample lesson remains playable/exportable if planner/TTS fails.
Browser playback | No long blocking render in UI; display status and play final MP4 smoothly on a modest phone.
