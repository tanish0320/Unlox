FOUR-PERSON TEAM WORKFLOW
Blu Visual Teacher Hackathon | Offline-first implementation blueprint
Prepared from the supplied six-page hackathon problem statement, with implementation recommendations and repository research clearly separated from mandatory requirements.
1. Team and hardware
Four-person team; two i5 13th-gen/16 GB laptops (one with NVIDIA RTX 3050) and two lower-end 8 GB laptops. Use the RTX laptop for model experiments and final integration, but the final demo must also work CPU-only. Lower-end laptops are suitable for UI, SVG scenes, schemas, tests and docs; avoid assigning them heavy model inference.
2. Role allocation
3. Shared contract before parallel work (first 45 minutes)
Create one Git repository and a shared branch strategy. Protect main; integrate through small pull requests or direct reviewed merges.
Agree the exact LessonPlan schema and allowed scene types: title_card, diagram, code_walkthrough.
Agree API endpoints: POST /api/lessons/generate; GET /api/lessons/{id}/status; GET /api/lessons/{id}; GET /api/lessons/{id}/video; GET /api/lessons/{id}/notes.
Create a sample lesson JSON and mock API response immediately so UI and scenes can proceed in parallel.
Decide one renderer by hour 1: Inkling-style HTML/SVG + Puppeteer + FFmpeg OR Remotion. Do not integrate both by default.
Agree the three demo languages and validate voice availability before promising them.
Add a README section for licences and a local/offline checklist from the beginning.
4. Parallel workstreams and interface details
Person 1 — AI, language and integration
Start with Ollama installed and a small model already downloaded. Test structured JSON output against the exact schema.
Implement planner adapter with timeout, one retry and deterministic fallback.
Benchmark local TTS on a short script in English and the two chosen Indian languages; do not assume a model is fast enough just because it runs.
Test IndicTrans2 only for selected language pairs and protect code tokens, numerals and technical terms.
Define audio manifest per scene: scene_id, file_path, duration_seconds, language, voice_id.
Integrate only through the agreed API/data contract; keep all inference local.
Person 2 — API, export and reliability
Implement request validation, job IDs/status, artifact storage and typed errors.
Build export from fixed sample scene assets first; output 1280×720 H.264 video and AAC audio.
Make the audio the source of truth for scene duration; add only a small transition/pause margin.
Generate JSON notes from the validated canonical plan, not from a separate unrelated prompt.
Add fallback MP4 and sample notes so a failed model cannot block the demo.
Write tests for malformed JSON, missing audio, missing font, FFmpeg failure and Wi-Fi-off operation.
Person 3 — frontend and player
Create a clean single-page form: topic, level, language, duration and Generate.
Implement progress states for planning, translation, narration, rendering and complete.
Use mock API responses and sample assets first; don't wait for backend to finish.
Implement play, pause, next scene, replay, caption visibility and progress display.
Add separate Download MP4 and Download JSON Notes actions, plus clear errors/retry.
Test a small mobile viewport and multilingual input labels.
Person 4 — scene engine and notes
Implement title_card with heading and caption area.
Implement diagram with typed nodes, labels and arrows; animate only from approved properties.
Implement code_walkthrough with code string, highlighted line numbers and visible output panel.
Add caption rendering with bundled Noto fonts for every chosen script.
Create notes JSON renderer/preview and fixtures for all three languages.
Write scene component tests using the agreed schema and ensure unknown scene type is rejected safely.
5. Integration gates
6. Git and collaboration rules
Suggested folders: frontend/src/components/scenes, frontend/src/components/player, backend/app/api, backend/app/schemas, backend/app/services/planner, backend/app/services/tts, backend/app/services/translation, backend/app/services/render, backend/app/services/export, assets/fallback, outputs/.
Person 1 owns final integration and release tagging; Person 2 reviews API/schema/export changes; Persons 3 and 4 avoid changing backend contracts without discussion.
Commit small vertical slices. Use the sample JSON as a shared fixture; avoid committing huge model files or generated videos unless needed for fallback.
Use a local config file or environment variables for paths, but no secrets or cloud API keys should be required.
Pin dependency versions and verify that all required assets are present before the offline test.
7. Daily stand-up format (every 2–3 hours)
What is working now? Show it running, not just describe it.
What exact artifact will be merged in the next two hours?
What interface/schema/API change is needed? Agree before editing.
What is blocked and who can unblock it?
Does the end-to-end sample still work after the last merge?
8. Feature-cut order if time slips
Never cut: MP4 export, JSON notes, local-only runtime, three scene types, three required languages, audio sync, fallback.
Cut first: voice choice, speed control, caching, extra scene types, sophisticated transitions, history/library, existing-MP4 support, chatbot.
Prefer clean SVG/CSS visuals and readable captions over cinematic effects.
Do not leave the offline verification until the final 10 minutes; test it at least once by hour 18 and again before the demo.
9. Demo rehearsal checklist
Turn Wi-Fi off before launching the app.
Start local services and verify models/assets load from disk.
Enter a fresh topic, choose a language and generate.
Show the lesson playing in browser with captions and scene controls.
Download and play the MP4; confirm 1280×720 and audio.
Download JSON notes and parse them with a JSON validator.
Stop Ollama or trigger a planner failure and show the fallback lesson still works.
Keep one known-good MP4 per required language on disk as a last-resort demo safety net.
10. Key recommendation
Your original idea to put the two 8 GB laptops on UI is sound, but split their work: one owns the application shell/player and the other owns the visual scene components and notes UI. Keep AI/model experiments on the RTX laptop, and put backend/export reliability on the other i5/16 GB laptop. All four work against one schema and one chosen renderer.
11. Exact repository usage and ownership
These are the repositories the team should actually plan around. The team should not clone every repository in the research list. Use the recommended path below, with one renderer and a tested local TTS stack.
12. Repositories explicitly NOT to integrate in the 24-hour MVP
OpenMAIC (https://github.com/THU-MAIC/OpenMAIC): useful classroom UX reference, but a broader application than needed. Do not make it the base unless the team has already verified every needed feature runs offline.
Chitralekha (https://github.com/AI4Bharat/Chitralekha): focuses on existing-video transcription/translation/voice-over, not topic-to-new-animated-video. Save it for a future uploaded-video workflow.
IndicConformerASR (https://github.com/AI4Bharat/IndicConformerASR) and WhisperX (https://github.com/m-bain/whisperX): not core requirements for generated narration when the TTS chunk duration is known. Add only if a measured need justifies the complexity.
Do not integrate Inkling and Remotion together by default. Pick one renderer.
Do not add hosted model providers, cloud TTS, cloud translation or remote asset loading.
13. Repo selection gate — finish by hour 1
Clone/install Ollama, the selected renderer, FFmpeg and frontend dependencies.
Generate one scene locally and export a short MP4 from a fixed sample.
Run a short TTS sample in English and both candidate Indian languages; record latency and memory.
Check IndicTrans2 quality and runtime only for the selected language pairs.
Select the final TTS and renderer based on working evidence, not README claims alone.
Keep model and voice licence details in README; never assume code licence covers model weights.
14. Revised final recommendation
Use a small custom React/Vite/TypeScript + FastAPI application. Adopt Ollama for the local planner; use Inkling as the first renderer reference plus FFmpeg for export; evaluate IndicTrans2 for translation and Kokoro ONNX / IndicF5 for local TTS. Use Remotion only as an alternative renderer. Do not integrate OpenMAIC or Chitralekha into the MVP. The team owns the schema, API and three scene components, which keeps the architecture simple and demoable offline.
15. Start all four teammates simultaneously — zero-wait kickoff
Goal: all four teammates should produce working code from the first hour, without waiting for the AI model, backend API or another teammate. The way to achieve this is to freeze a tiny contract, provide fixtures/mocks, and split work by files and interfaces.

Choose a single package manager (npm) and Python environment strategy (venv + pinned requirements). Do not let each teammate invent a different setup.
Freeze the LessonPlan schema and three scene types: title_card, diagram, code_walkthrough.
Create one fixtures/sample-lesson.json plus fixtures/sample-notes.json and mock job-status responses. Everyone can work against these immediately.
Agree file ownership and route contracts below. Changes to shared schema require a quick group decision.
Pick one renderer by minute 20: Inkling-style HTML/SVG + browser capture + FFmpeg is the default; Remotion is the alternative, never both initially.

15.3 Freeze these contracts so no one blocks anyone
15.4 Git strategy for parallel work
Use one shared repo with main as the known-good branch and four branches: feat/local-ai, feat/backend-export, feat/ui-player, feat/scene-components.
Each teammate commits only their owned files initially. Avoid simultaneous edits to shared schema, package.json or API client contracts.
Person 2 creates the initial schema/fixture, then announces the version; thereafter schema changes are coordinated rather than silently edited.
Person 3 and Person 4 can work in the same frontend repo because their file ownership is separated; Person 3 owns the shell/player, Person 4 owns scenes/notes components.
Use local mock responses so frontend development is not blocked by the API. Person 2 uses fixed audio and sample plan so export isn't blocked by model work.
Merge at least every 2–3 hours; don't wait until the end. Person 1 is integration lead, Person 2 reviews schema/export, and each author tests their slice.

15.6 Rules to preserve parallelism
Every task must have an independent fixture and a clear output artifact.
Never block UI work on Ollama; never block MP4 export on a live model response.
Never block scene work on TTS; use prerecorded audio and duration fixtures initially.
Keep one renderer, one schema and one API contract.
Run the offline end-to-end test early and again after final integration.
At hour 5, all four streams should already have working slices; if not, reduce scope and remove integration blockers.
